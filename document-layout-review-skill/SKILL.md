# document-layout-review

## 强制执行流程（不可跳过）

**建立基准 → 全面检查 → 形成问题清单 → 分类修复 → 重新渲染 → 验收 → 未通过则继续修复**

以上流程为强约束，必须按顺序执行，不得跳过步骤或提前交付。每轮修复后必须重新检查、渲染和验收；未通过则返回对应修复步骤。无法完成时说明原因，不得宣称验收通过。

## 1. 建立排版基准

样式优先级：

1. 用户在当前任务中明确提出的格式要求；
2. 用户当前上传的 Word 模板；
3. 项目已经确认的模板；
4. `assets/default-template-style.json` 与 `assets/default-template.docx`；
5. 都不存在时才使用通用排版规则。

有模板时，先读取模板实际样式，不凭经验猜字体、字号、行距、标题、表格或页面设置。

用户上传的模板内部存在冲突时，停止修复并让用户选择。

### 标题编号同样以模板为准

同时读取实际模板的 `styles.xml`、`numbering.xml`、层级绑定及实际示例；不仅复制字体。编号字形、前后缀、分隔符、编号后的空格/制表符和重启方式都属于模板约定。**待修文档不是编号基准；即使旧编号已经是自动编号，只要不符合模板，也必须纠正。**

本仓库已确认的默认模板采用 `1`、`1.1`、`1.1.1` 等阿拉伯数字，编号后为空格，不带“第…章”。使用其他已确认模板时读取其真实约定，不能把这个例子硬编码到所有模板。修复绑定段落和标题样式两处，使后续新增同级标题仍自动续号；目录由 Word 更新，不手写目录数字。

### 修复边界：修问题，不重新设计

没有用户要求或适用于该对象的明确模板依据，不得改变原有配色、底色、边框风格、图形形状和装饰。**原来没有底色，也是一种必须保留的外观状态。** 不能因为“更统一”“更专业”添加表头灰底，或把原图换成另一套绘图风格。

模板只约束其明确规定的对象和属性；不得用模板里出现次数最多的表格样式推断整份文档的外观。确有明确改色/改样式要求时，单独按该要求应用并记录来源、对象及变化，核对后建立本轮批准基准；不得把越权修改后的候选文件反过来当基准。

保留原始 Word 和原图供最终对照。每轮修复按 `references/mutation-scope-contract.md` 先快照、再修改、再比较；比较失败即回滚，不能只凭“看起来没问题”放行。此边界不替代原有字体、标点、空格和自动编号检查。

### 本次文字规则

Agent 将用户明确提出的正文要求写入本次任务的 `text-rules.json`，未提及的项目沿用模板和 `assets/default-text-rules.json`。默认保留正文黑体（`黑体` / `SimHei`），但用户明确禁止或指定替代字体时，以用户要求为准。

初检、模板应用、修复和复查统一传入 `--text-rules <同一份规则文件>`；不要临时修改脚本或永久修改默认规则。未知字段、规则冲突或无法确定替代字体时，先说明并确认，不得忽略要求后继续交付。接口与示例见 `references/text-rules.md`。

模板解析和冲突处理细则见 `references/template-resolution.md`。

## 2. 先检查，不要边看边改

先对整个文档建立问题清单，再开始修改。

至少检查以下 8 类：

1. **模板与真实样式使用**
   - 正文、标题、表格、题注是否真正使用了正确样式；
   - 字体、字号、粗体、斜体、行距、缩进、段前段后是否被 direct formatting 污染；
   - 逐个检查可见文字 run 的字体、字号、直接粗体/斜体；按第 1 节的本次文字规则判断，不按异常覆盖比例放行；
   - 正文加粗/斜体按本次规则检查；默认清除与正文基准冲突的直接加粗/斜体，保留允许的字符样式强调；
   - 页面、页眉页脚是否符合模板。

2. **标题与正文**
   - 标题层级和同级一致性；
   - 孤立标题；
   - 异常粗体、斜体、字体、字号、缩进、行距；
   - 空段、重叠、裁切、超出正文区域。

3. **表格**
   - **先理解表头、每列用途、正文内容量和行之间的分组关系，再判断布局；不得只检查是否越界。**
   - 检查表格总宽度是否超过当前节可打印宽度；普通表格不得靠扩大页面或改横向来容纳；
   - 检查每列宽度是否同时匹配**表头字数、列语义和正文内容压力**。序号/状态/数量等短列应紧凑，名称/类别等中等列应适中，要求/响应/说明/措施/备注等长文本列应获得更多空间；
   - 检查是否存在“一列特别窄、一列无必要地特别宽”的突兀比例；相邻列宽度反差必须能够由内容量和语义解释，不能机械照搬旧模板比例；
   - 模板已有同表头列宽只能作为**参考基准**。当前内容明显不同或渲染效果不协调时，必须按当前内容重新平衡，禁止“模板有这个比例所以直接照抄”；
   - 检查“一字一行”、表头被拆得过碎、长文本列严重拥挤等窄列问题；
   - 检查长 URL、路径、标识符、连续数字/英文等不可断行字符串；不得因为单个长串让 Word 自动调整列宽并把整张表或页面异常拉宽；
   - **检查同一列连续重复文字是否属于同一个语义分组。** 对“标的名称、项目名称、工作对象、类别、阶段、模块、工作包”等分组列，如果连续多行确属同一对象，应纵向合并重复单元格；如果各行是独立记录、独立状态或独立响应，则不得仅因文字相同而合并；
   - 合并后不能破坏其他列与行的对应关系，不能丢内容，不能制造跨页边框或阅读歧义；
   - 单元格是否上下居中；
   - **表格内所有文字首行缩进必须为 0**，不得继承正文的 2 字符首行缩进；
   - 表头、内边距、文字样式、跨页和重复表头是否合理；
   - 默认技术标模板启用时，技术偏离表必须遵循已确认的物理网格结构：**6 个语义列、7 个物理列，“招标技术要求”占两列，其中一列为星号/三角标识列。**

   检查时必须运行 `scripts/table_layout_audit.py`。该脚本负责发现可确定的宽度/越界/窄列/自动拉伸风险，并输出 `review` 级纵向合并候选；**`review` 不是自动合并指令，Agent 必须结合表格语义逐项决定。**

4. **图片与流程图**
   - 是否清晰、变形、裁切、越界；
   - 对象清单必须覆盖真实图片、流程图、架构图、技术路线图和原生 Shape；不能因为没有 `flowchart.json` 或没有箭头，就当作没有需检查的图。
   - 先看提取的完整原图，再放大检查节点、文字边界、连线、标签和可读性；原生 Shape 没有媒体文件时先渲染原 Word。文字出框、重叠、裁切、内嵌外部题注属于硬缺陷，必须修复。
   - 区分“图片像素内的图号/题注”和“Word 页面上独立的图题”，不能只凭整页截图误删正常图题。
   - 初检与终检使用 `figure_review.py` 的逐对象清单；`flowchart_audit.py` 只验证语义数据，不能替代实际看图，也不能证明图片中文字不出框。

5. **页面与分节**
   - 页面尺寸、方向、页边距、分节、页眉页脚、空白页、孤立页是否正确；
   - 不允许为了塞下表格或图片擅自改变页面方向。

6. **空格**
   - 中文字符之间、中文标点前后、中文括号/引号内外、段首段尾、表格单元格首尾的无意义空格；
   - 必须检查跨 run 边界的空格，以及全角空格、不换行空格（NBSP）、零宽空格等不可见脏字符；
   - **中文日期、时间、数量表达中的数字与单位不得夹无用空格**，例如 `2026 年 10 月 31 日` 必须修为 `2026年10月31日`，`软件 1 套` 修为 `软件1套`，`报告 2 份` 修为 `报告2份`；
   - 不误删英文、代码、路径、URL、公式中的合法空格，也不把 `中文 API` 这类明确的中英混排单空格一概删除。

7. **标点**
   - 中文语境用全角中文标点；
   - 英文、代码、公式、命令、URL、路径用半角标点；
   - 中文引号必须是 `“……”`；
   - 禁止明显错误或重复标点。

8. **标题、题注与脚注自动编号**
   - 标题使用与实际模板一致的多级自动编号和真实标题样式；不能从坏文档推导“第一章/第1章”等新格式。
   - 图和表分别在每个一级章节从 1 递增；显示 `图1 题名`、`表1 题名`，不显示章节前缀，不用 `STYLEREF` 拼图号。题注为独立 Word 段落，图下表上；图片本体不得烧录外部图号和题注。
   - 根据真实图表清单检查缺注；Agent 结合内容和上下文补题名，程序插入原生 `SEQ` 域。装饰图、封面标志和布局表需确认用途后豁免，不乱加“图1”。
   - 脚注仍使用原生脚注引用及自动序号。
   - 手工数字、普通上标和写成文字的域代码不算自动编号。已有自动编号同时符合模板和本次规则时才保持不变；手工编号转为自动编号，保留业务文字和真实层级，编号形式遵循本次模板与题注规则。
   - 先识别真实标题、题注和脚注，不把封面标题、目录项、正文列表、参考文献或公式指数当作转换对象。
   - 必须运行 `scripts/numbering_audit.py`；无法确定层级、序列或脚注引用关系时，由 Agent 核对后处理，不得跳过并记为通过。

推荐先运行 `scripts/inspect_document.py` 生成结构化检查结果，但脚本结果只是问题证据，不替代 Agent 对页面和视觉内容的判断。

## 3. 给问题分类

### A. 可确定性自动修复
例如：模板样式未应用、正文中违反本次规则的字体、字号、普通正文中误加的局部或整段直接粗体/斜体、行距缩进错误、单元格未上下居中、表格越出可打印宽度、明确空格和标点错误。

直接修。

### B. 需要理解内容后修复
例如：表格列宽重新分配、连续重复单元格是否应纵向合并、分页位置、流程图重绘、图片缩放和复杂视觉布局。

先理解内容和上下文，再修。**程序给出的列宽建议和合并候选只是证据，不替代语义判断和最终页面判断。**

### C. 必须用户确认
例如：模板内部存在两个都合理但互相冲突的样式；修复可能改变业务含义；流程图原始连接关系无法确定；表格是否合并会改变业务记录含义且现有内容无法判定。

停止自动选择，询问用户。

详细修复策略见 `references/repair-playbook.md`。

## 4. 修复顺序

优先按下面顺序处理，减少互相覆盖：

1. 模板/样式基准；
2. 标题/题注/脚注自动编号，再处理正文、标题、字体、字号、字重、斜体、行距、缩进；
3. 表格；
4. 图片和流程图；
5. 页面与分节；
6. 空格和标点；
7. 最终细节。

### 自动编号

识别对象与引用关系 → 读取实际模板编号 → `numbering_repair.py` → 原有文字/样式修复 → 用同一模板复核并恢复标题/题注规则 → 实际更新域 → `numbering_audit.py` → 渲染复查。

初检、修复和终检统一传入实际 `--template`、`--template-style-json`。正文图表引用先唯一定位，再改为“见下图/见上图/见下表/见上表”；跨越同类对象或有歧义时由 Agent 精确调整，不改成含糊的“见相关图表”，不把图片文件名当引用。

缺题注的题名由 Agent 看内容后写入 `object-plan.json`，程序负责定位、插入、计数与验收。这个计划是 Agent 的内部工作，不要求用户逐张填写。详见 `references/caption-and-image-review.md`。

编号转换独立执行，不以重新手写数字代替。断号、重复号、混合编号、复杂域或脚注配对不明确时，先由 Agent 核对；有必要时使用 `--numbering-plan` 提交已确认的位置。接口、范围和示例见 `references/numbering-rules.md`。

### 表格

列宽修复只动布局属性，不得修改 `tblStyle`、`tblLook`、底色、边框色或文字颜色；不得套用模板中最常见的 Table Style。表格字体、首行缩进为 0 等仍由原有文字样式步骤处理，先完成并复查，再单独修列宽。合并等语义结构变更仍须单独核对，不能夹在宽度修复里执行。

表格修复必须按以下顺序：

1. 识别表头和每列语义；
2. 读取当前节可打印宽度；
3. 统计表头长度、正文平均内容量、较长内容和最长内容；
4. 给短列设可读的最小宽度；
5. 将剩余宽度优先分给长文本列；
6. 检查相邻列是否出现无依据的极端宽窄反差；
7. 检查长 URL/路径/标识符是否存在自动拉伸页面风险；
8. 检查连续重复分组列，结合行语义决定是否纵向合并；
9. 同步修复 `tblGrid`、`tcW`、表格总宽度、对齐、单元格边距和重复表头；
10. 重新渲染真实页面检查视觉协调性。

**不要把“整体缩字号”“把页面改横向”“模板原来就是这个列宽”作为列宽问题的默认解决办法。**

最终要求是：短列不空旷、长列不拥挤、表头和正文都可读、列宽变化有内容依据、整张表看起来协调，没有明显突兀的宽窄比例。

### 图片与流程图

**先区分“图本身有问题”与“图在当前页放不下”，不能把占用空间大当作重绘理由。**

原图语义和视觉正常时：

**保留原图 → 在保持比例和可读性的前提下调整大小/位置 → 当前页放不下则让“图 + 图题”独占一页 → 重新渲染检查。**

独占一页允许合理增加页数。保持原页面尺寸、方向和页边距，图题与图同页；不得删除或挪乱章节内容，不用空段堆出新页，也不为填满新页把图片拉伸变形。纯缩放/定位使用 `image-layout`；只调整现有段落分页标志使用 `figure-pagination`。二者分轮检查，原图片媒体和图内内容必须不变。

只有图内文字出框、节点重叠、连接歧义、图内明确文字错误、在独占页和合理缩放后仍不可读等真实缺陷无法靠文档布局解决，或者用户明确要求重新设计时，才进入重绘。原图不清晰时先取得清晰源图；无法确认文字或连接关系不得猜画。

确需重绘：

**查看完整原图 → 确认具体缺陷 → 重建并核对节点/连线语义 → 保留原配色、方框/圆角、字体风格、分组和主阅读方向进行必要调整 → 原图与新图并排比对 → 替换回 Word → 再看最终页面。**

不得仅为套用绘图脚本的默认颜色、圆角或图形规范而改造正常原图。重绘不是重设计；脚本不支持复现源风格时，使用能保留源风格的绘制方式，不得拿默认效果直接替换。用户明确要求新风格时才按其要求改变。

### 正文局部字体/字号/字重

逐个处理普通正文 run：

- 按本次规则保留允许的字体，修复禁止或不符合基准的字体；同时检查段落样式、字符样式的继承结果；
- 字体、字号、加粗和斜体分别处理，修改一个属性时不得连带清除其他允许保留的属性；
- 默认按正文基准修复字号和直接加粗/斜体；用户明确要求保留、禁止或统一时，按本次规则执行；
- 用户只要求保留黑体字体时，不等于要求保留加粗；
- 局部异常也要修，修复后使用同一份规则再次执行 run 级审计。

### 标点和空格

只改字符本身，不为了修标点重建段落或破坏原有 run 的字体、字号、粗体、斜体。

空格修复必须基于整段可见文字判断，因此即使空格与相邻文字分属不同 run，也要识别并删除；中文标点后的空格、中文左括号/左引号前的空格同样属于检查范围。

日期、时间和中文数量单位执行确定性规则：数字与 `年/月/日/号/时/分/秒` 之间不得有空格；数字与 `套/份/台/个/项/次/人/家/组/类/页/章/节/条/款/批/处/点/座/册/张/幅/米/公里/平方米/万元/亿元` 等中文单位之间不得有空格；中文名词后紧跟“数字 + 中文数量单位”时，名词与数字之间的无用空格也要删除。

## 5. 每轮修复后都重新检查

一轮修复完成后：

1. 检查 DOCX 结构和内容完整性；
2. 检查模板真实使用情况；
3. 检查表格/图片/流程图结构；
4. 对表格重新运行 `scripts/table_layout_audit.py`，并按本轮 scope 运行 `scripts/layout_invariant_guard.py compare` 检查越权变化；
5. 实际更新最终 DOCX 的域与目录，重新检查结果和原生域结构，再将**最新 DOCX**渲染为页面图片；
6. 逐页检查最终页面。

不要检查旧截图。写入 `updateFields=true`、手填正确缓存数字或只有一个 `PASS` 字符串，不等于实际执行 F9。使用 `field_refresh.py` 调用真实 Office 引擎；没有可用引擎时保留“待验证”，不得宣称完整验收通过。刷新引擎若丢失章节重启开关或改坏模板样式，同样不通过。

最后一次图片修复后使用 `review_pipeline.py --audit-only` 重新验收，不重跑大批样式/布局修复去覆盖已修好的图片。每轮仍执行对应 scope 快照比较。

最终文字及编号验收必须运行：

- `scripts/numbering_audit.py`：标题多级编号、题注域、脚注引用及自动序号；存在 `error` 或未解决的 `review` 时不得交付；
- `scripts/template_usage_audit.py --text-rules <本次规则文件>`：run 级字体、字号、加粗和斜体；
- `scripts/hard_text_audit.py`：字符级标点/空格；
- `scripts/table_layout_audit.py`：表格宽度、列宽内容匹配、窄列/拉伸风险、技术偏离表物理结构及纵向合并候选。

其中：

- `table_layout_audit.py` 存在 `error`：不得交付；
- 存在 `review`：Agent 必须逐项结合语义判断，完成合并或明确确认无需合并，并在最终页面复核；
- 确定性检查全部通过，也仍然不能跳过最终页面视觉检查。

## 6. 验收标准

最终交付前必须全部 PASS：

- 内容完整，没有丢字、重复、误删或改变事实；
- 标题编号及样式与实际模板相符，后续新增标题仍绑定同一层级列表；不保留错误的“第…章”写法；
- 图表分别章内从 1 计数，图下表上，缺注已补，图片内部没有烧录外部题注；正文上下图/表引用对象和位置正确；
- 最后修改后已实际更新域并重新审计，没有“错误！未定义样式。”、手工固定序号或断裂引用；
- 模板实际样式使用正确；
- 正文和标题没有异常字体、字号、粗体、斜体、行距、缩进；**正文字体、字号、加粗和斜体符合本次规则，用户未提出的项目沿用原基准**；
- 表格不越界，列宽与表头/正文内容量匹配，相邻列没有无依据的突兀宽窄反差；
- 表格无明显一字一行、无自动拉伸页面风险，长文本列拥有合理空间；
- 应纵向合并的连续分组单元格已经合并；不应合并的独立记录保持独立；
- 表格上下居中、表内首行缩进为 0、跨页可读；
- 表格无未经授权新增/改变的底色、边框色、文字颜色或条件样式；
- 图片清晰、不变形、不裁切；仅调整图片大小/位置/分页时，原媒体及图内内容保持不变；
- 确需重绘的图已与原图并排检查，原有良好风格未被默认配色或圆角覆盖；独占页的图与图题同页，前后正文完整；
- 流程图及架构图文字不出框、节点不重叠；箭头或分组关系正确。初检缺陷已逐项关闭；图内容未变时不得把图内缺陷改写成“已修复”；
- 页面尺寸、方向、页边距、分节、页眉页脚正常；
- 中文/英文标点符合语境；
- 无确认出的无用空格；中文标点前后、括号/引号周边、跨 run 边界、日期/时间/数量单位以及全角/NBSP/零宽空格均已检查；
- 最终页面没有肉眼可见的排版缺陷。

完整验收清单见 `references/acceptance-checklist.md`。

## 7. 验收失败就回到对应步骤

任意一项 FAIL：

1. 记录页码、对象和问题；
2. 归类到模板/正文/表格/流程图/页面/文字；
3. 回到对应修复步骤；
4. 只修改引发 FAIL 的对象；
5. 重新生成 DOCX；
6. 重新检查；
7. 重新渲染；
8. 再验收。

一直循环到全部 PASS，或遇到必须由用户确认的问题。

**最后一次修改后没有重新渲染和验收，就不能宣称完成。**

## 8. 交付

最终同时交付修复后的 Word 和一份简短的修复报告（Markdown）。

报告说明主要改了哪里、怎么改的，以及仍未解决或需用户确认的问题（如有）。同类批量修改可合并说明，不必逐项罗列；只记录实际生效的修改，未验证的不要写成已通过。

必须通过 `scripts/finalize_review.py` 生成交付 Word。新版入口要求完整的确定性检查、真实域更新记录、逐页和逐图复查；缺项目、旧哈希、未关闭的图内缺陷均拒绝输出。不得直接把 `candidate.docx` 改名绕过交付检查。

不得交付未验收的中间文件。技能和脚本不能控制宿主是否绕过入口，也不能替代模型真实看图；宿主级禁止绕过需由其工具权限/交付 hook 实现，不作“提示词绝对保证”的承诺。
